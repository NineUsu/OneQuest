# OneQuest mockup

Tools and Mentors/Coworker : Claude Opus5.5

Inspiration & Credit to: Gapminder Tools

หน้าเว็บตัวอย่างของ OneQuest: แผนที่ปัญหาและโอกาส (กราฟฟองสบู่ ขนาดปัญหา × ระดับที่ถูกละเลย), สัญญาณรายวัน, การตรวจสอบหลักฐาน และอันดับโอกาส

**ข้อมูลใน `web/data.json` ตอนนี้เป็นข้อมูลสมมติทั้งหมด** หน้าเว็บจะขึ้นแถบเตือนเองเมื่อ `is_sample` เป็น true

## โครงสร้าง

```
pipeline/problems.json   รายการปัญหาที่ติดตาม (แก้ไขเพิ่มลดได้)
pipeline/build_data.py   ดึงข้อมูล คำนวณคะแนน คัดกรองหลักฐาน แล้วเขียน web/data.json
web/index.html           หน้าเว็บ (HTML ไฟล์เดียว ใช้ ECharts จาก CDN)
web/data.json            ข้อมูลที่หน้าเว็บอ่าน
.github/workflows/daily.yml   ตัวอย่างให้ GitHub รันทุกเช้าและเผยแพร่หน้าเว็บ
```

## รันบนเครื่องตัวเอง

ต้องมี Python 3.9 ขึ้นไป ไม่ต้องติดตั้งไลบรารีเพิ่ม

```bash
python pipeline/build_data.py          # สร้างข้อมูลตัวอย่าง
python pipeline/build_data.py --live   # ดึงข้อมูลจริงจาก World Bank, OpenAlex, GDELT
cd web && python -m http.server 8000   # แล้วเปิด http://localhost:8000
```

ต้องเปิดผ่าน http.server เพราะเบราว์เซอร์ไม่ยอมให้หน้าเว็บอ่าน data.json ถ้าเปิดไฟล์ตรงๆ

## เอาไปรันที่ไหนได้บ้าง

หน้าเว็บเป็นไฟล์ static ล้วน วางบนที่ไหนก็ได้ที่เสิร์ฟไฟล์ได้ ส่วนสคริปต์ Python ต้องมีที่ให้รันวันละครั้ง

| ทางเลือก | หน้าเว็บ | รันสคริปต์รายวัน | ค่าใช้จ่าย |
|---|---|---|---|
| GitHub Pages + GitHub Actions | ✓ | ✓ cron ในไฟล์ workflow | ฟรีสำหรับ repo สาธารณะ |
| Cloudflare Pages / Netlify / Vercel | ✓ | ใช้ GitHub Actions คู่กัน หรือ scheduled function | มีแผนฟรี |
| VPS หรือคอมพิวเตอร์ตัวเอง | ✓ (nginx หรือ http.server) | ✓ cron | ตามเครื่อง |
| Google Cloud Run / AWS Lambda + S3 | ✓ | ✓ Cloud Scheduler / EventBridge | จ่ายตามใช้ |

เมื่อเริ่มมีคนตรวจหลักฐานหลายคน ค่อยย้ายข้อมูลจาก JSON ไปฐานข้อมูล (เช่น Supabase หรือ PostgreSQL) และทำหน้าสำหรับทีมตรวจ

## แผนลงมือและตลาดงาน

แต่ละปัญหาใน `problems.json` ใส่ฟิลด์ `plan` ได้ แตกเป็น สาเหตุย่อย (`causes`) → แนวทาง (`approaches`) → เควสต์ (`quests`) โดยเควสต์แต่ละชิ้นระบุว่าใครทำได้ ใช้ทักษะอะไร ใช้เวลาเท่าไร ผลลัพธ์ที่วัดได้คืออะไร และมีคนรับไปกี่คน ส่วน `plan.labor` เก็บอาชีพที่เกี่ยวข้อง (รหัส ISCO-08) และแหล่งข้อมูลตลาดงานที่ต้องเก็บ

`build_data.py` คำนวณตำแหน่งงานที่ต้องมีจาก demand ÷ `people_per_worker` และถ้ารู้ `current_workers` ก็คำนวณตำแหน่งที่ยังขาด นอกจากนี้ยังนับเควสต์ที่ยังไม่มีคนรับ

ฟิลด์อื่นใน `plan`:
- `kind` ของแนวทาง: แก้ต้นเหตุ / สร้างความสามารถ / บรรเทาเฉพาะหน้า
- `level` และ `fields` ของเควสต์: ระดับ (เริ่มต้นไม่ต้องมีพื้นฐาน) และสาขาที่ต้องใช้
- `predict`: คำถามให้ทายก่อนดูข้อมูล หน้าเว็บเก็บคำตอบไว้ในเบราว์เซอร์ของแต่ละคน
- `why_unsolved`: เหตุผลที่ปัญหายังอยู่ แยกตามประเภท เช่น ต้นทุน เจ้าภาพ ข้อมูล

ส่วน "รูปแบบร่วมข้ามปัญหา" (`patterns` ใน data.json) รวมประเภทของ `why_unsolved` และ `fields` จากทุกปัญหา เพื่อดูว่าต้นเหตุและสาขาไหนเกิดซ้ำในหลายเรื่อง ตอนนี้มีแผนตัวอย่าง 3 เรื่อง คือผู้ดูแลผู้สูงอายุ ฝุ่น PM2.5 และหนี้ครัวเรือน ตัวเลขทั้งหมดยังเป็นค่าสมมติ

## การตรวจสอบหลักฐาน

ระบบอัตโนมัติยืนยันไม่ได้ว่าข้อความในข่าวหรืองานวิจัย "จริง" ทำได้แค่คัดกรองให้คนตรวจเร็วขึ้น `build_data.py` จึงแบ่งเป็น 4 ขั้น

1. **ดึงเข้ามา** จาก GDELT (ข่าว ทุก 15 นาที), OpenAlex (งานวิจัย), World Bank (ตัวเลขทางการ ปีละครั้ง)
2. **ให้น้ำหนักตามชั้นของแหล่ง** งานวิจัยที่ผ่าน peer review และสถิติทางการ > ข่าว > โซเชียล
3. **หาแหล่งยืนยันข้าม** ข่าวขึ้นสถานะ "มีแหล่งรองรับบางส่วน" เมื่อมีอย่างน้อย 2 แหล่งที่เป็นอิสระต่อกันพูดถึงเรื่องเดียวกัน
4. **คนตรวจ** สถานะ "ยืนยันแล้ว" หรือ "ขัดแย้ง" ต้องมี `reviewed_by` เสมอ

ขั้นที่ควรเพิ่มต่อ: ใช้ LLM ดึงตัวเลขและข้อกล่าวอ้างออกจากข่าวมาเทียบกับตัวเลขทางการ, ตัดข่าวซ้ำที่มาจากต้นฉบับเดียวกัน, และเก็บประวัติว่าใครตรวจอะไรเมื่อไร

## สิ่งที่ยังไม่ได้ทดสอบ

โหมด `--live` เขียนตาม API ที่เปิดให้ใช้ฟรีของทั้งสามแหล่ง แต่ยังไม่ได้รันจริง เพราะเครื่องที่สร้าง mockup เข้าถึงอินเทอร์เน็ตภายนอกไม่ได้ ตัวชี้วัด World Bank ใน problems.json เป็นตัวแทนคร่าวๆ ควรเลือกใหม่ให้ตรงกับแต่ละปัญหา และคะแนน 4 ด้านยังเป็นค่าที่ใส่เอง ยังไม่ได้คำนวณจากข้อมูล
